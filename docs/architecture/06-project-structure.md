## 6.2 Docker Compose services

| Service | Image / build | Port (host) | Purpose |
| --- | --- | --- | --- |
| `postgres` | `postgres:16-alpine`, volume `postgres16_data` | 4000 -> 5432 | Database; init script creates `tasktrack_owner` and `tasktrack_app` |
| `redis` | `redis:7-alpine` | 4001 -> 6379 | Celery broker, cache, throttles |
| `s3` | `chrislusf/seaweedfs:4.54`, profile `s3` only | 9000 -> 8333 | Optional S3-compatible store, used when `USE_S3=true`; creates the private bucket on start |
| `mailhog` | `mailhog/mailhog` | 1025 (SMTP), 8025 (UI) | Captures all mail in dev |
| `migrate` | backend image | none | One-shot `manage.py migrate` as `tasktrack_owner`, then `seed_rbac` |
| `api` | `./backend` | 8000 | Django (runserver in dev, gunicorn in prod), runs as `tasktrack_app` |
| `worker` | `./backend` | none | `celery -A config worker` |
| `beat` | `./backend` | none | `celery -A config beat` |
| `web` | `./frontend` | 3001 | Next.js |

Start order: `postgres`, `redis` healthy, then `migrate` completes, then `api`, `worker`,
`beat`, then `web`. Volume `media_data` holds local files when `USE_S3=false` (default).
To use S3 locally: `USE_S3=true docker compose --profile s3 up -d`.

## 6.3 Environment variables

See `.env.example` in the repository root for the full list with defaults. Groups:
Django core, database (app and owner URLs), Redis/Celery, JWT and cookies, file storage (`USE_S3`, media root, S3 settings),
email, security (field encryption key, CORS, CSRF origins), observability (Sentry,
log level), frontend (`API_INTERNAL_URL`).

## 6.5 CI (GitHub Actions)

`.github/workflows/ci.yml`, on push and pull request:

| Job | Steps |
| --- | --- |
| `backend` | Services postgres:16 + redis:7; same role init script as compose; `ruff check` + `ruff format --check`; `makemigrations --check`; `check --deploy` with prod settings; `pytest --cov`; `spectacular --validate --fail-on-warn`. Schema diff against `frontend/openapi.json`. |
| `frontend` | `npm ci`, `eslint`, regenerate API types + `git diff --exit-code`, `tsc --noEmit`, Vitest |
| `compose` | `docker compose config`, production backend image build |
| `e2e` (Phase 7) | `docker compose up -d --wait`, seed, Playwright, upload traces on failure |

## 6.6 Testing strategy

Backend (pytest, pytest-django, factory_boy, pytest-xdist, freezegun):

| Area | Approach |
| --- | --- |
| Tenant isolation | Parametrised matrix generated from the URL resolver: for every endpoint and method, a user from company A calls it with IDs from company B. Expect 404 (or empty list), and expect company B rows unchanged. A meta-test fails if a new endpoint is not covered |
| RLS | Tests switch to `SET ROLE tasktrack_app` and run raw SQL without context (expect zero rows) and with the wrong company (expect zero rows, `INSERT` rejected) |
| RBAC | Matrix tests: for each (role, permission, scope) in the seed, positive and negative cases using the policy API and the endpoints |
| State machine | Every default rule: allowed actor succeeds; wrong role, wrong scope, missing comment, missing reviewer, dependency blocked, locked task all fail with the documented code |
| Review | submit with incomplete checklist, double submit, approve by non-reviewer, request changes without comment, round numbers, history, lock after approval, reopen |
| Tokens | Invite and reset: expiry (freezegun), single use, revoke, resend invalidates old, hash-only storage, no enumeration |
| HR restrictions | Rank matrix for reset, deactivate, role assignment |
| Timer concurrency | Two threads starting timers for the same user against real Postgres (transactional test case): exactly one succeeds; partial index verified |
| Audit | Meta-test: every non-GET endpoint invoked with valid input produces at least one `AuditLog` row with correct actor and company; `UPDATE`/`DELETE` on audit table raise at DB level |
| Optimistic locking | Stale `version` returns 409 |

Frontend: Vitest + Testing Library for components, hooks and Zod schemas; MSW to mock the
generated client in unit tests only. Playwright against the real compose stack for core flows:

1. HR creates employee, invite email in MailHog, employee sets password, auto-login, logout, login.
2. Manager creates and assigns task, member starts timer, completes checklist, submits, manager requests changes, member resubmits, manager approves, task is read-only.
3. Theme toggle persists; key pages pass `@axe-core/playwright` with no serious violations; mobile viewport (390x844) smoke for sidebar drawer, task list and timer bar.
